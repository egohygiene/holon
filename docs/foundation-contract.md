# Repository foundation contract

Status: **v1 draft, executable**  
Owner: `egohygiene/holon`

## Purpose

Holon is the organization bootstrapper and repository foundation compiler. This
contract establishes a small vocabulary for describing what a repository is and
which reusable organizational capabilities it needs. It does not copy source
code between sibling repositories and it does not own the implementation of
those capabilities.

The compilation boundary is:

```text
repository manifest + pinned organization contracts
                    |
                    v
       validation and deterministic resolution
                    |
                    v
       future render/apply plan with owned paths
```

## Repository classes

| Class | Intended use | Security floor | Typical sites |
|---|---|---|---|
| `library` | Independently consumed package | `baseline` | docs, architecture |
| `tool` | Standalone executable or developer tool | `hardened` | landing, docs, architecture |
| `product` | User-facing application or service | `hardened` | landing, docs, architecture |
| `publication` | Research or multi-channel publication | `baseline` | docs, architecture |

Each class has three capability sets:

- `required_capabilities` cannot be disabled by a repository.
- `default_capabilities` are applied unless explicitly excluded.
- `allowed_capabilities` are opt-in extensions permitted for the class.

Capability dependencies are added transitively. Unknown capabilities,
dependency cycles, conflicts, and attempts to weaken a security floor fail
resolution.

## Ownership boundary

Holon owns the manifest grammar, resolution rules, future render engine, and
generated-path ledger. Capability implementations remain with their domain
owners:

- Hygiene owns holistic architecture context.
- Empathy owns community-health policy.
- Aether owns provider-neutral agent capability projections.
- Relay owns reusable CI and release workflows.
- Egolint owns quality profiles.
- Realm owns development/runtime environment projections.
- Beacon owns publication and PDF production contracts.

The `owner` field in the capability catalog makes that dependency explicit.

## Pinning policy

Every manifest pins the architecture and foundation contracts. Aether and Realm
pins become mandatory when their capabilities are selected. Mutable references
such as `main`, `latest`, `edge`, and `dev` are invalid. OCI inputs require a
full `sha256` digest; Git inputs require a version tag or commit hash.

This keeps a generated plan reproducible even while the organization moves
quickly.

## Idempotent update model

A future `holon apply` operation must preserve this model:

1. Resolve the same manifest and pins to byte-for-byte equivalent structured
   output.
2. Render only paths declared as generated by the selected capabilities.
3. Never overwrite `preserve_paths` or unmanaged repository files.
4. Record the generator version, inputs, rendered paths, and content digests.
5. Produce a reviewable plan before changing an existing repository.
6. Remove a previously generated file only when the ledger proves ownership and
   the new plan explicitly withdraws it.

This issue implements steps one and the policy inputs for steps two through six.

## Example manifests

The examples are conformance fixtures, not recommended repository names or
release versions. The all-zero Realm digest is deliberately syntactically valid
fixture data and must be replaced with a published image digest before a real
repository is provisioned.

## Non-goals for v1

- Rendering repository files.
- Installing tools directly.
- Storing credentials or secret values.
- Defining Realm's internal package/profile model.
- Reimplementing the capabilities owned by other repositories.
