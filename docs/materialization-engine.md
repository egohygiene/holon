# Holon materialization engine

Holon materialization turns a resolved repository foundation manifest into a reviewable filesystem plan, applies that plan only after an explicit render step, verifies generated ownership, and provides a bounded rollback path.

The engine introduced for HOL-02 is intentionally local and provider-light. It does not fetch mutable sibling repositories or silently execute external generators. Sibling capabilities remain owned by their source repositories and enter Holon through pinned artifacts or already-rendered pack inputs.

## Lifecycle

```text
foundation manifest
      ↓ HOL-01 resolution
resolved manifest
      ↓
plan ────────────────┐
      ↓ review       │ input/target drift
render               ├────> reject and re-plan
      ↓              │
state + provenance ──┘
      ↓
verify
      ↓
rollback (when required)
```

The four stateful boundaries are separate commands. `plan` is dry-run only. `render` refuses to proceed when the reviewed plan no longer matches the current target or current artifact inputs.

## Commands

Create a plan:

```sh
python3 tools/holon_materialize.py plan \
  --manifest "examples/tool.manifest.json" \
  --target "/tmp/example-tool" \
  --aether-source "/path/to/pinned/aether/dist" \
  --render-source "/path/to/rendered-pack" \
  --render-overlay "/path/to/derived-profile-overlay" \
  --output "/tmp/example-tool.plan.json"
```

Apply exactly that reviewed plan:

```sh
python3 tools/holon_materialize.py render \
  --plan "/tmp/example-tool.plan.json" \
  --target "/tmp/example-tool" \
  --aether-source "/path/to/pinned/aether/dist" \
  --render-source "/path/to/rendered-pack" \
  --render-overlay "/path/to/derived-profile-overlay"
```

Verify generated files against recorded hashes:

```sh
python3 tools/holon_materialize.py verify \
  --target "/tmp/example-tool"
```

Roll back the latest render:

```sh
python3 tools/holon_materialize.py rollback \
  --target "/tmp/example-tool"
```

## Plan contract

Plans use `holon.materialization-plan/v1` and are timestamp-free. Their `plan_id` is the SHA-256 digest of the canonical plan payload, so identical manifest, inputs, and target state produce the same plan.

Each operation is one of:

- `create` — target path does not exist;
- `update` — the path is Holon-owned, has not changed since the prior render, and desired bytes changed;
- `delete` — a previously Holon-owned path is no longer emitted and is still byte-identical to the prior state;
- `noop` — generated content is already current;
- `preserve` — the manifest explicitly places the path inside a user-owned preserve boundary;
- `conflict` — applying automatically would risk overwriting or erasing user-owned state.

A plan containing any conflict is not renderable.

## Generated ownership

Holon records state at:

```text
.holon/materialization-state.v1.json
```

Every managed file records:

- repository-relative path;
- SHA-256 of generated bytes;
- owning source (`egohygiene/holon`, `egohygiene/aether`, and later versioned providers);
- a provenance/source descriptor.

The state file is evidence, not permission to overwrite arbitrary content.

### First materialization

If a desired target path already exists and is not recorded in Holon state, Holon reports a conflict even when the bytes happen to match. Adoption of pre-existing user files is a separate future workflow; v1 does not silently take ownership.

### Updates

Holon updates a previously managed file only when the current bytes still match the SHA-256 stored by the previous render. A manual edit produces a conflict and requires human reconciliation.

### Removed outputs

When an output disappears from the desired materialization, Holon deletes it only when the bytes still match prior generated state. Modified or missing prior outputs are treated as drift rather than silently reconciled.

### Preserve paths

`preserve_paths` are hard user-ownership boundaries. Holon never writes or deletes paths at or beneath one of those entries. If a previously generated path becomes preserved, the next successful render relinquishes Holon ownership without deleting it.

The `.holon/` state namespace itself cannot be listed as preserved or supplied by a render source.

## Rollback

Each successful render writes immutable rollback evidence beneath:

```text
.holon/backups/<plan-id>/attempt-NNN/
```

The backup contains:

- the previous Holon state when one existed;
- prior bytes for each updated/deleted generated file;
- a `holon.materialization-rollback/v1` operation record.

Rollback is fail-closed. Before restoring anything it verifies that files created or updated by the render still have the exact post-render digest. If a human changed a generated file after render, rollback stops rather than deleting that change. A path deleted by render must still be absent before rollback can restore its prior bytes.

Backup attempts are retained as audit evidence, so an identical plan may be applied again after rollback without overwriting its earlier backup record.

## Generic rendered-pack adapter

`--render-source` is the neutral filesystem adapter for Holon-owned or externally prepared packs. It recursively projects regular files from a supplied directory and rejects symlinks, path traversal, `.git`, and `.holon` targets.

UTF-8 text may use a deliberately small token vocabulary:

```text
{{repository}}
{{repository_name}}
{{repository_class}}
{{security_level}}
{{parameter.<key>}}
```

Scalar manifest parameters are substituted as text. Structured object and array parameters are substituted as canonical JSON, which lets typed source modules consume one reviewed manifest contract without a separate generator. Any unresolved Holon token fails planning. Binary files are copied byte-for-byte.

`--render-overlay` is a repeatable, ordered derivative-profile input. Each overlay is validated and hashed with the same rules as the base render source, then deliberately replaces colliding base paths. Plans and materialization state preserve the source and overlay index for every managed file. A changed, reordered, added, or removed overlay changes the deterministic `plan_id`; `render` therefore requires the exact same ordered overlay list used by `plan`.

This replacement behavior is limited to explicitly supplied overlays. It does not relax the engine's protection of pre-existing consumer files or manually changed managed files.

This adapter is how later blueprint issues can feed rendered source into the materialization engine without coupling the engine to React, LaunchKit, Zensical, Flutter, or another framework.

## Aether release adapter

When the resolved capability list includes `aether-agents`, planning requires a local `--aether-source` pointing at a previously acquired **pinned Aether distribution**. Holon does not fetch Aether's default branch.

The adapter validates:

1. the manifest's immutable `pins.aether` reference;
2. `release/release-manifest.v1.json`;
3. `release/release-provenance.v1.json`;
4. `projections/manifest.v1.json`;
5. each selected provider output against both projection and release provenance hashes.

Supported native repository projections are:

| Aether provider | Source in Aether distribution | Consumer destination |
| --- | --- | --- |
| `github-copilot` | `github/repository/.github/agents/` | `.github/agents/` |
| `vscode-copilot` | shared GitHub repository projection | `.github/agents/` |
| `claude-code` | `claude/repository/.claude/agents/` | `.claude/agents/` |
| `opencode` | `opencode/repository/.opencode/agents/` | `.opencode/agents/` |

Provider selection is controlled by the optional manifest parameter:

```json
{
  "aether_providers": ["github-copilot", "claude-code"]
}
```

The default is `github-copilot`. Providers marked `manual-import` by Aether (currently Zencoder) are rejected as native materialization targets rather than being treated as ordinary files.

A manifest may also set `"github_mcp": true` to project Aether's verified secret-free GitHub MCP template to `.mcp.json`; credentials remain outside Holon and outside generated source.

## Capability boundary

HOL-02 builds the stateful engine, not every capability pack. The resolved manifest still lists every selected capability. The plan records the adapter class for each capability:

- `aether-agents` uses the pinned Aether release adapter;
- other capabilities use `render-source-or-specialized-pack` until their owning Holon/sibling issue publishes a concrete adapter or pack.

This prevents the materializer from pretending that unresolved Relay, Realm, Hygiene, site, or framework work has been implemented merely because the capability exists in the foundation catalog.

## Safety and determinism

- Planning and rendering make no network requests.
- Plans contain hashes and provenance, not copies of source file contents.
- Absolute source-machine paths are not embedded in plans or state.
- Source trees are hashed by sorted repository-relative path plus content digest.
- Filesystem writes use atomic replacement.
- A render re-plans immediately before mutation and requires the same `plan_id`, closing the plan/apply time-of-check gap.
- An unexpected filesystem failure triggers best-effort restoration from the pre-render backup.
- `/` and the user's home directory are rejected as direct materialization targets.
- `.git` is never a valid generated path.
- There is no v1 force-overwrite switch.

## Future adapters

The engine is intentionally ready for later issues to provide bounded sources such as:

- Hygiene repository-context projections;
- Empathy community-health baselines;
- Relay reusable workflow callers;
- Egolint quality profiles;
- Realm devcontainer profiles;
- React/Vite, LaunchKit, Zensical, and other Holon packs.

Those adapters should produce deterministic desired files or a rendered-pack directory and must preserve the ownership rules defined here.
